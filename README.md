# IntDeliv — заявки Della → Lardi

Сам збирає свіжі заявки Della (ціна від 8000, прямий замовник тощо), складає в базу й автоматично
публікує на кілька акаунтів Lardi (до 5) через офіційний API. Обрані замовники — вгорі й першими в черзі,
чорний список — не показуються й не публікуються. Без Chrome, без серверів і сторонніх акаунтів.

- **Адмінка:** https://intdeliv.siteboosty.com/ (GitHub Pages, гілка `gh-pages`, `./deploy.sh`).
- **Рушій:** GitHub Actions (`.github/workflows/engine.yml`) — працює безперервно, щохвилини опитує Della.
  API віддається через безкоштовний тунель trycloudflare (без акаунта); адмінка бере адресу з `api.json` у гілці `data`.
  Кожен запуск (~5,7 год) сам ставить у чергу наступний (`server/successor.mjs`), розклад — лише запасний:
  GitHub запускає його нерегулярно. Запуск у черзі тримає код, з яким його поставили, тож після пушу в `main`:
  `gh workflow run engine.yml --ref main` (замінить того, що чекає), а щоб перейти негайно — ще й `gh run cancel <id поточного>`.
- **База:** SQLite, між запусками зберігається в гілці `data` лише стиснутою й зашифрованою
  (`intdeliv.sqlite.gz.enc`: gzip → AES-256, секрет `DB_KEY`; `server/persist.sh`). Старий файл `intdeliv.sqlite.enc`
  відновлення теж читає; перше ж збереження замінює його новим.

Секрети репозиторію: `ADMIN_KEY` (ключ входу в адмінку), `DB_KEY` (шифрування бази),
`LARDI_TOKEN_1`, `LARDI_TOKEN_2` (необовʼязково — токени вписуються в налаштуваннях адмінки й зберігаються
лише в зашифрованій базі), `DELLA_COOKIE` (необовʼязково, запасний шлях — сесію Della краще вставити в адмінці, див. нижче).
Ручний запуск: Actions → engine → Run workflow.

**Сесія Della і чорний список:** без входу Della не показує в картці замовника (ні компанії, ні телефону), тож
чорному/білому списку нема з чим порівнювати. Пароль із сервера не підходить (на вході Della reCAPTCHA), тому береться
кука браузера, де клієнтка вже увійшла: Chrome → della.com.ua → DevTools → Network → будь-який запит до della.com.ua →
Request Headers → `Cookie` — скопіювати й вставити в адмінці (RPC `della.session.set`; порожньо — стерти). Рушій ходить
на Della з цією сесією, інакше з `DELLA_COOKIE`, інакше без входу. Сесія лежить лише в зашифрованій базі: у журнал,
відповіді RPC і помилки не потрапляє (`settings.get` віддає тільки `{set, state, checkedAt, updatedAt}`).
`della.session.check` бере одну сторінку першого пошуку й каже чесно: `alive` (замовника видно), `blind` (вхід є,
замовника нема — напр., акаунт не верифікований), `expired` (Della відповіла як без входу), `error`, `none`.
Збір сам помічає, що сесія закінчилась, і пише про це в журнал один раз. `status.get` показує `della` і
`custCoverage` (у скількох заявок є замовник). Чорний список догоняє вже зібрані заявки: кнопкою (`customers.reapply`)
і сам — у перевірці актуальності раз на 10 хв, до 100 заявок за прохід.

Ключ замовника — **телефон або назва компанії**, кожного досить (а також код Della й ЄДРПОУ). Назва порівнюється
без форми власності (ТОВ, ФОП, повна «Товариство з обмеженою відповідальністю», «TOB» латиницею), регістру, лапок,
різних апострофів і різниці між дефісом і пробілом. Ключі, внесені за старими правилами, міграція при старті переписує
один раз і жодного запису без ключа не лишає; що не розв'язала (два записи на одну фірму, назва без змісту) —
у `customers.list` → `nameKeyIssues` і рядком у журналі; у спорі чорного з білим перемагає чорний.
З чорного списку замовник не виходить випадково: `customers.add` / `customers.move` (і злиття записів), що забрали б
чорний ключ в «Обрані», і `customers.remove` запису, який зараз у чорному списку (за базою, не за копією списку в клієнта),
відповідають відмовою `code: 'fromBlack'` з `data: {action: 'add' | 'move' | 'remove', list ('white'; null — прибрати), entries: [{id, list, label, keys}], loads}`;
після підтвердження людиною адмінка повторює виклик із `fromBlack: true` (лише буквально `true`) і отримує `visible` / `queued`
(`affected.*` в add/move, у корені відповіді — в remove). `loads` і `visible` — лише заявки, які справді знову видно: ту, що й далі
ховає інший чорний запис, не рахуємо; `restored` / `queued` — теж лише заявки цієї дії. «Прибрати» з «Обраних» — без прапорця, як і було.
Так само й `loads.update`: правка телефону / компанії / ЄДРПОУ, після якої заявку вже не ховав би чорний список, без
`fromBlack: true` — відмова `data: {action: 'edit', list: null, loadId, entries, loads: 1, outcome: 'queued' | 'new' | 'archived' | 'inactive'}`
(нічого не записано); з прапорцем — правка проходить, відповідь — заявка + `affected: {visible, restored, archived, queued, entries}`.
Правка, що з чорного списку не виводить (ціна, коментар, інший запис і далі ховає), — без прапорця, як і була.
Позначку «чорний список», під якою вже немає жодного чорного ключа в базі (ні за колонкою, ні за даними замовника), звіряє
staleCheck: заявка повертається в роботу (і в чергу, якщо автопублікація) або в Архів (дата минула / давно не видно в Della),
до 100 за прохід, одним рядком журналу. Заявку, що підпадає під будь-який чорний ключ, звірка не чіпає ніколи. `della.session.check` каже, що саме дає Della з цим входом
(`sample.has`: телефон / назва / код / ЄДРПОУ, `cards`: у скількох картках видно замовника) і як тоді блокувати;
«вхід працює» — лише коли замовника видно щонайменше в третині карток. Те саме з останньої перевірки чи збору
`status.get` віддає в `della` (`has`, `phoneSeen`, `cards`) без запиту до Della.
Телефон за «Докладніше» Della віддає лише через `POST /ajax_private_list_card.php` (JS Della, 05.11.2026): кожен запит —
зі свіжою капчею браузера (reCAPTCHA v3 або hCaptcha + BotD), а контакти бачить лише верифікований акаунт із пакетом
підключення. Сервер капчі не проходить і обходити її не буде, тож запит контактів (`della.contacts`) вимкнено:
увімкнений, він питає лише нові заявки без телефону, до 10 за збір, і після першої відмови чи помилки (капча, доступ,
HTTP 403/429/5xx, мережа) до нової сесії мовчить.

Код: `extension/lib` — спільні модулі (парсер Della, клієнт Lardi, фільтри), `worker/src` — рушій і RPC,
`server/` — запуск рушія в Node + збереження бази, `admin/` — адмінка. Тести: `node --test tests/*.test.mjs`
і атакувальний набір тестувальника `node --test tests/qa/*.qa.mjs` — обидва мають бути зелені.

**Адмінка локально (без сервера й без ключа):**

```sh
python3 -m http.server 8000 -d admin
```

Відкрити http://localhost:8000/?demo — демо-режим: заготовлені заявки, акаунти Lardi й замовники
(обраний і два в чорному списку, в одного «на Lardi ще 1 — знімаємо»); вкладка «Замовники» — http://localhost:8000/?demo#customers.
Дії в демо нічого нікуди не надсилають. Без `?demo` — звичайний вхід за ключем (кнопка «Подивитись демо» там теж є).

**Зняття з Lardi:** якщо Lardi не відповів під час зняття (чорний список, неактуальна заявка), рушій добирає залишок
сам — у перевірці актуальності раз на 10 хв, до 100 публікацій за прохід, кожну лише раз.
